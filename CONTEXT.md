# Context: Agentic Developer Core

This document serves as the canonical glossary of domain concepts for the autonomous development loop. It is devoid of implementation details (such as LangGraph nodes or CLI options) and focuses purely on terminology.

## Glossary

- **Autonomous Developer Loop**: The end-to-end lifecycle of an issue being processed by the agent. It spans from claiming a ticket to planning, execution, verification, pull request creation, and merging.
- **Orchestrator**: The high-level coordinator that manages the lifecycle of the loop, guiding work through the distinct phases and handling high-level routing, errors, and task assignment.
- **Worker**: The active agent that performs the actual code-writing, searching, and code modifications within the codebase workspace.
- **Workspace Hygiene**: The practice of cleaning and resetting the workspace (e.g., git cleaning, directory resetting) to guarantee a consistent environment.
- **Stateful Resume**: The capability of the loop to recover from a crash or system restart and resume execution from the exact phase and task it was working on, preserving in-progress work.
- **Verification**: The process of running tests, linters, or other build checks to ensure that modifications meet quality standards and do not introduce regressions.
- **Verification Feedback**: The truncated execution output (maximum 150 lines or 10 KB) captured from a failed verification subprocess. This feedback is persisted in the orchestrator state and fed back to the worker agent in subsequent execution turns to guide self-correction.
- **Block-Based Patching**: The method of modifying code by replacing an exact, unique block of lines (`old_string`) with a replacement block (`new_string`), rather than using line numbers or diff syntax.
- **File Creation**: The first-class path by which the Worker creates a **new** file via `patch_file` with an empty `old_string` and the full content as `new_string`. Distinct from Block-Based Patching (which edits existing files): creation is **exempt** from the Read-Before-Edit Constraint — there is no prior content to read — but the exemption applies *only* when the file genuinely does not exist; creating an existing file is rejected (no silent overwrite), directing the Worker to read-then-edit instead. Creation goes through the identical Path Safety Validation as edits (blocked paths fail closed), creates parent directories automatically, and does not register `read_files` membership — a subsequent edit on the freshly-created file still requires a `read_file` first. Established by ADR-0048 to eliminate the brittle `run_command` heredoc workaround for new files.
- **Planning**: The phase of the autonomous developer loop where the orchestrator uses a language model to analyze a claimed issue alongside a static codebase snapshot to produce a **Localization** — a set of target files and task intents. The plan points the Worker at *where* to work, not *what diff to write*.
- **Localization**: The Plan-Node's output: which files and structural elements (classes, methods, functions) the Worker should touch, plus the intent of each task. Localization never includes line numbers or diff shapes — those are the Worker's responsibility.
- **Edit Synthesis**: The Worker's responsibility during the Execute phase: reading the localized files, reasoning about surrounding code, and writing the actual patches. The plan provides the target; the Worker discovers *how* to make the change through dynamic exploration (read, grep) and ReAct reasoning.
- **Process Supervisor**: A lightweight, zero-dependency Python wrapper (implemented in `scripts/entrypoint.py`) that acts as the entrypoint for the orchestrator container. It validates essential environment variables, verifies network reachability to external services, and manages a resilient execution loop for the orchestrator with exponential crash backoff.
- **Read-Before-Edit Constraint**: A strict safety rule requiring the Worker to programmatically read a file's contents in the current cycle before applying any patches to it, eliminating hallucinated or stale edits. The constraint is **range-scoped** (ADR-0033): reading a partial line range (`start_line`–`end_line`) authorizes edits *only* within that range, while reading the whole file (no bounds) authorizes edits anywhere in it. `patch_file` locates the `old_string`'s line span and rejects the edit if any of those lines fall outside the union of previously read ranges. The record of read ranges (path → list of `[start, end]` inclusive intervals) is reset at the start of each phase and upon stateful resume.
- **Path Safety Validation**: The programmatic blocking of sensitive paths (credentials, private keys, certificate extensions, and VCS/dependency/agent-state directories) from Worker tool access, via the shared `is_safe_path` blocklist. Enforced at two layers: **pre-flight** (the Plan-Node rejects sensitive *planned* target files before execution, ADR-0012) and **runtime** (the `read_file` and `patch_file` tools reject sensitive paths at tool-call time, ADR-0035). The runtime layer closes the read-then-patch bypass — an agent could otherwise read a sensitive file, gain `read_files` membership, and patch it despite the pre-flight block — and mitigates symlink/TOCTOU drift between the static plan and dynamic execution.
_Avoid_: path check, sensitive-path guard, file safety
- **Hybrid Retry Strategy**: The Execute→Verify retry policy that refines ADR-0013's pure Incremental Refinement. Execute attempts below a configurable threshold (`AGENT_RETRY_HARD_RESET_ATTEMPT`, default 3) keep the workspace intact so the Worker patches its prior edits; from the threshold attempt onward, the Execute-Node reverts tracked-file edits to `HEAD` (`git reset --hard`) so the Worker retries from a clean branch state instead of building on compounding errors. Only tracked files are reverted — untracked files (notably the Test-Writer's tests and stubs) are preserved, since nothing is committed until the PR-Node. Prior verification feedback is still injected on the reset attempt (Reflexion): the clean slate is the workspace, not the Worker's memory.
_Avoid_: hard rollback retry, clean-slate retry, reset retry
- **Merge-Fix Loop**: The post-PR counterpart to the pre-PR Hybrid Retry — a bounded, deterministic graph edge that closes the judge-feedback loop. When the Merge-Node parses actionable PR Review Judge verdicts (`FAIL`/`NEEDS REVIEW`, ADR-0014) and the budget is not exhausted, the graph routes `merge → execute`; the judge findings are injected into the existing `Verification Feedback` channel so the Worker self-corrects, the PR-Node commits a `fix:` commit and re-pushes, and the Merge-Node re-polls a fresh CI run + judge review. The budget is bounded by `AGENT_PR_FIX_MAX` (default 3, not the human-steered skill's 15 — each headless iteration pays a full CI round-trip). At exhaustion, a summary PR comment is posted before transitioning to Failure Recovery, replacing the prior silent re-queue. Distinct from Hybrid Retry (pre-PR, `verify → execute`) and from Verification Feedback (the channel both loops reuse).
_Avoid_: post-PR retry, judge-fix loop, autofix loop
- **Strict Pre-Commit Gate**: An opt-in, developer-invoked security tier distinct from Verification. Verification is the fast, deterministic, in-cycle gate (lint, type-check, tests) the autonomous loop runs up to 3×; the Strict Pre-Commit Gate layers security-sensitive static analysis on top of the fast deterministic checks, invoked on demand rather than enforced on every commit. It mirrors the CI security scan locally, reducing detection latency for security-sensitive changes from CI (minutes–hours) to commit time (seconds), at the cost of developer flow speed when invoked. Opt-in by design: the default developer flow prioritises speed; strict scanning is a developer choice, not a mandate. Distinct from the CI enforcement layer, which remains the authoritative hard gate.
_Avoid_: strict pre-commit hook, security pre-commit, strict scan
- **Blocked by**: A structured markdown section (`## Blocked by`) in an issue body containing references to other issues (e.g., `- #123`). The Orchestrator parses this section, transitioning the issue's label to `agent-blocked` if any referenced issues are open, and restoring it to `agent-ready` once all dependencies are closed.
- **Target Repository**: The remote GitHub repository containing the issues to resolve and the codebase to modify (specified via `GITHUB_REPOSITORY`).
- **Orchestrator Repository**: the codebase of the autonomous developer loop itself — the Python project containing the Orchestrator, Worker, scripts, and CI workflows. Distinct from the Target Repository: the Orchestrator Repository is what the autonomous loop is built from; the Target Repository is what the autonomous loop acts on. PR Review Judges evaluate PRs to the Orchestrator Repository, not the Target Repository.
_Avoid_: own repo, self repo, this repo
- **Workspace Isolation**: The sandboxing of all worker file edits and command executions inside the local directory specified by `GITHUB_WORKSPACE`, keeping it separate from the orchestrator's own codebase and state logs.
- **Self-Healing Claim**: The two-step programmatic polling process in the Claim-Node that automatically unblocks issues when their dependencies close (transitioning them from `agent-blocked` to `agent-ready`), and claims eligible issues (transitioning them from `agent-ready` to `agent-in-progress`).
- **Pull Request Creation**: The phase of the autonomous developer loop where a pull request is opened to propose the verified codebase modifications for review.
- **Merge Polling**: The process of repeatedly checking the merge status of an open pull request until it is successfully merged or a timeout occurs.
- **PR Body Enrichment**: The deterministic composition of the human-facing pull-request body (the only human-facing artifact the autonomous loop produces) from plan rationale, a `git diff --stat` summary, and the verify run's test-coverage tail — all derived from existing state and git signals with **no additional LLM call**. Built once at Pull Request Creation; each section degrades to a short note when its input is absent rather than raising, so the PR is always created. Distinct from the PR Review Judges, whose inputs (the git diff only) are unaffected by the body — Judge Neutrality is preserved by input hygiene, not by the body's contents. Mirrors the Implementation Leakage concern: the body surfaces the *plan's rationale*, never the Worker's specific implementation choices.
_Avoid_: PR description generation, PR summary, autonomous PR body
- **Failure Recovery**: The safety process triggered upon total execution failure or timeout, which cleans up local changes and restores the issue's GitHub label back to its ready state, allowing for future attempts.
- **Telemetry**: The mechanism used to collect, record, and export OpenTelemetry-compliant trace spans (such as `orchestrator_loop` and `orchestrator_phase_...`) in-process during the autonomous developer loop execution, supporting crash-resistant JSONL logging and OTLP exporting.
- **Worker Tool Trust Boundary**: The boundary between the Worker's *untrusted* primary input (the Target Repository's GitHub issue body, which is attacker-controllable and concatenated into the Worker prompt) and its *trusted* tool-execution surface (Worker Tools). Because the Worker runs unattended and holds file-system and command-execution tools, the issue body is treated as adversarial data, not instructions; defense-in-depth controls ensure the boundary fails closed even if the LLM is fully prompt-injected — a compromised Worker cannot read secrets (Path Safety Validation across the whole read surface), cannot exfiltrate them via commands (a `run_command` binary allowlist with a minimal allowlist environment), cannot reach internal hosts via outbound fetch (URL Fetch DNS pinning), and any residual secret that reaches a tool result is redacted before it is persisted to a Worker Trace or exported via Telemetry. Distinct from Workspace Isolation (which confines *where* the Worker writes) — this confines *what* a compromised Worker can reach across the boundary.
_Avoid_: tool sandbox, agent boundary, input boundary
- **Test Writing**: The phase of the autonomous developer loop (implemented in the Test-Writer Node) where the orchestrator uses a language model to write unit/integration tests for the planned changes before implementing them, enforcing Test-Driven Development (TDD) principles.
- **Implementation Leakage**: The risk that Test-Writer-generated tests encode a specific implementation (internal data structures, private/dunder attributes, return types, or method signatures beyond the public contract) rather than observable behavior, indirectly steering the Worker toward the Test-Writer's assumed solution instead of an independent one.
_Avoid_: test coupling, over-specification, structural testing
- **Worker Tool**: A capability exposed to the ReAct Worker agent within the Execute phase (e.g., `read_file`, `patch_file`, `grep_search`, `run_command`). Worker Tools are invoked on-demand by the agent based on what it observes, following the ReAct pattern — not as static pipeline stages. A `web_search` Worker Tool lets the agent research library APIs or error messages inline, only when it encounters a gap it cannot resolve from the codebase alone.
- **Pre-PR Review**: A semantic code-quality grading step within the Verification phase, executed after the deterministic verification command (`make verify` by default, configurable via `AGENT_VERIFY_COMMAND`) passes and before a Pull Request is created. Uses a BinEval rubric (binary checks across Completeness, Simplicity, ADR Compliance, Robustness) graded by a lightweight LLM. Failures produce structured feedback fed back to the Worker for in-cycle retry. Acts as a soft gate — it does not block progression permanently.
- **BinEval**: The binary (pass/fail) rubric and grading pass that powers the Pre-PR Review. Ten checks across four dimensions (Completeness, Simplicity, ADR Compliance, Robustness), graded by the `bin_eval` node's flash LLM against a language-agnostic input set (issue body, plan, git diff, ADRs). The factory node name is `bin_eval` (snake_case, per ADR-0018); the telemetry phase span is `orchestrator_phase_bineval` (per ADR-0016). An LLM/infrastructure failure degrades to PASS — the post-PR Review Judges are the hard gate.
_Avoid_: binEval, binary eval, pre-PR judge
- **Length-Limit Budget Retry**: The single, enlarged-`max_tokens` retry attempted inside the BinEval call when the first attempt returns `finish_reason=length` with no parseable verdict (ADR-0049). A reasoning model can exhaust the entire `max_tokens` budget on `reasoning_tokens` before emitting the verdict, producing a length-limit truncation that — without the retry — silently degrades the soft gate to PASS with no grading at all. The retry multiplies the configured `max_tokens` (default 2×, capped, env-overridable) and fires **exactly once**, then degrades to PASS. It is a *budget* retry, not a semantic retry: it does **NOT** consume `attempts["bineval"]` (ADR-0047) — the semantic budget counts genuine BinEval FAILs, while a length-limit truncation is an infrastructure failure categorically distinct from a judgment failure. Non-reasoning models never produce `finish_reason=length`, so the retry path is dead code for them. Distinct from the BinEval semantic retry (a genuine FAIL looping back to Execute with structured feedback).
_Avoid_: token retry, truncation retry, length retry
- **Judge Neutrality**: The contract that PR Review Judges evaluate the diff strictly on its own merits, unswayed by metadata or anchoring. A shared neutrality preamble (`=== 0. JUDGE NEUTRALITY ===`) is prepended to every judge system prompt, addressing the LLM-as-a-Judge biases documented in the "Justice or Prejudice?" study (arXiv:2410.02736): (1) ID/metadata bias — do not infer the author or generation method (human, AI, or automated agent); (2) anchoring bias — do not anchor on any description of intent beyond what the diff and context demonstrate; (3) ADR over-weighting — assess genuine adherence to documented rules, not mere citation of an ADR (the one bias source genuinely present, since the architecture judge receives every ADR); (4) position bias — weigh each finding independently of its position. The judge inputs already exclude author and issue-body metadata, so neutrality is enforced both by input hygiene (the metadata is never provided) and by the preamble (defense-in-depth). Distinct from position-bias mitigations for pairwise-comparison judges (order swapping, dual-order evaluation), which do not apply to these single-input PASS/FAIL/NEEDS REVIEW scorers.
_Avoid_: bias mitigation, judge fairness, neutral judge
- **PR Review Judges**: The hard merge-gate evaluation that runs as a CI check on PRs to the Orchestrator Repository. Comprises multiple specialized LLM judges (Syntax/Lint, Test Coverage, Architecture Compliance, Security) each producing a verdict, posted as a single GitHub review with a hidden verdict block (ADR-0019). During Merge Polling, the orchestrator's `merge_node` parses that hidden block and blocks the merge on any `FAIL` or `NEEDS REVIEW` verdict (ADR-0014). The judges evaluate Orchestrator Repository code, not Target Repository code.
- **CI Coverage Output**: The CI-produced test-execution and coverage report (pytest with `--cov-report=term-missing`) captured to a file and passed to the Test Coverage PR Review Judge via the `CI_COVERAGE_OUTPUT_PATH` environment variable (ADR-0030). The judge consumes it — it runs no language-specific tooling itself (Language Agnosticism) — to determine whether the production code changed in the PR is actually exercised by passing tests, beyond the diff-only Test Presence / Test Quality checks. Tail-bounded to a character budget (`CI_COVERAGE_OUTPUT_MAX_CHARS`); absent or empty output degrades gracefully to the diff-only evaluation, never spuriousizing the hard gate.
- **Empty Content Response**: A structurally valid OpenRouter response (`{"choices": [{"message": {"content": ""}}]}`) where the `content` field is empty or whitespace-only. Passes API-level structural validation but carries no evaluative signal. Retried pre-emptively inside the LLM call's retry loop (not post-hoc in evaluation), distinguishing it from a genuine `NEEDS REVIEW` verdict.
_Avoid_: blank response, empty verdict
- **Fallback Indicator**: A visible notice rendered in the PR review body when a judge's final verdict was produced by the fallback model rather than the primary. Surfaced per-judge so a human reviewer can see which verdicts came from a substitute model.
_Avoid_: fallback flag, model swap note
- **Enclosing Function Context**: Additional source code appended to the judges' input beyond the raw git diff: for each changed hunk, the full body of the enclosing function or class method, read from the workspace checkout. Reduces false-positive findings caused by the diff's ±3 line context window being too narrow to judge duplication, assertion quality, or taint flow. Bounded per-file at 15,000 characters. Applied to both the PR Review Judges (inside `run_judge`, per-chunk) and the BinEval soft gate (inside `_run_bineval_phase`), via the shared `scripts/enrichment.py` module (ADR-0032).
_Avoid_: function snippet, code context, surrounding code
- **Language Agnosticism**: Applies exclusively to the Verification path. The Verify Node and its BinEval review operate on language-agnostic inputs (git diff, issue body, generated plan, ADRs). The orchestrator never assumes the Target Repository's programming language for verification — language-specific deterministic checks (lint, type-check, security scans, test coverage) are the Target Repository's own responsibility, enforced via the verification command it provides to the orchestrator — `make verify` by default, configurable via `AGENT_VERIFY_COMMAND` (timeout `AGENT_VERIFY_TIMEOUT`, default 300s) for target repositories without a Makefile.
- **Language-Aware Best-Effort Planning**: The Plan-Node, unlike Verification, is permitted to use language-aware signals. It applies structural outline extraction for supported languages (Python, TypeScript) and falls back to the directory tree for unsupported ones. This is a pragmatic tiering, not agnosticism: supported languages get a richer Localization snapshot; unsupported ones still function via the tree alone.
- **Structural Outline**: A compact representation of a source file's declarations — classes, interfaces, type aliases, enums, and method/function signatures *with parameter lists and return types*, extracted without file bodies, docstrings, or comments. Appended to the codebase snapshot in the Plan-Node prompt as a Localization aid. Parameter lists disambiguate methods with similar names across files. Outlines are *hints*, not ground truth: a misparsed signature is a planning signal, not a contract. The Worker's Read-Before-Edit Constraint remains the safety net against hallucinated edits.
- **Outline Fidelity**: Outlines for all supported languages (Python, TypeScript) are produced by tree-sitter via `tree-sitter-language-pack` — a single dependency providing pre-built grammar wheels with one unified query API. Both languages get robust, accurate outlines from the same tool. Unsupported languages (Go, Rust, etc.) fall back to the directory tree alone. Adding a new language's outlines requires only its tree-sitter grammar, not a new hand-rolled parser.
- **Plan Detail Request**: An optional field in the DevelopmentPlan output allowing the planner to request full Structural Outlines for specific files it needs to plan accurately — typically files whose outlines were truncated by the cap, but any file may be requested. If non-empty, the Plan-Node fetches those outlines (validating each exists and has a supported extension, silently skipping hallucinated or non-existent requests), enriches the prompt, and re-invokes the LLM once — the second plan replaces the first entirely, no merging. Bounded to a single follow-up call — the Plan-Node is not a ReAct agent and does not explore freely; it makes one targeted request for more detail, then produces the best plan it can. The Worker compensates for any remaining gaps during Execute.
- **Web Search**: A Worker Tool that invokes OpenRouter's server-side `web_search` tool, letting the Worker research library APIs, error messages, or unfamiliar patterns inline during the Execute phase. Search runs server-side at OpenRouter, so SSRF risk is near-zero.
- **URL Fetch**: A Worker Tool that retrieves the text content of a specific URL (e.g., a documentation page found via Web Search). Enforces SSRF protection (blocks private, loopback, link-local, reserved, multicast, and unspecified IP ranges) and optional domain allowlisting via `config/sources.toml`. Response is truncated to a maximum length to bound token consumption.
- **Trace Export**: The mechanism by which recorded telemetry spans are sent to an external collector for visualization and analysis. When `LANGFUSE_PUBLIC_KEY` and `LANGFUSE_SECRET_KEY` environment variables are set, spans are exported to Langfuse Cloud with Basic auth, and session-level baggage (`langfuse.session.id`) is attached to group all traces for a single issue cycle. When Langfuse keys are absent, spans fall back to the generic OTLP endpoint (`OTEL_EXPORTER_OTLP_ENDPOINT` or `host.docker.internal:4318`). This preserves the graceful degradation mandated by ADR-0016: tracing never breaks execution if the exporter or library is unavailable.
- **Worker Trace**: A serialized record of the Worker's full ReAct conversation (AI reasoning, tool calls, tool results) persisted to a JSONL file under `.agent_logs/` after each Execute attempt. Used exclusively for post-hoc debugging and observability — it is never loaded back into the loop or injected into retry attempts. The retry feedback mechanism remains the truncated Verification Feedback (Reflexion pattern), not raw trajectory replay.
- **Test-Writer Trace**: A serialized record of the Test-Writer's full ReAct conversation, persisted to its own JSONL sidecar (`test_writer_trace_<issue>_<attempt>.jsonl`) distinct from the Worker Trace to avoid filename collisions. Same serialization mechanism and post-hoc-only purpose as the Worker Trace.
_Avoid_: test trace, writer trace
- **Recursion Budget**: The LangGraph-native cap (`recursion_limit`) bounding a Worker's ReAct loop — a crash guard against infinite loops, not a measure of task size. Each think→tool round consumes 2 supersteps (agent node + tools node), so the limit approximates twice the tool-iteration count. Resolved per-node alongside Model Config (via `resolve_model_config()`, ADR-0045), supporting distinct budgets for Execute-Node vs Test-Writer-Node, with environment override (`{NODE}_RECURSION_LIMIT` / `AGENT_RECURSION_LIMIT`). Exhausting it raises `GraphRecursionError`; exhausting it does not, by itself, mean the task failed — only that the reasoning loop was bounded.
_Avoid_: recursion limit, step cap, iteration limit
- **Graceful Budget Exhaustion**: The call-site handling (Layer 3 of the three-layer Recursion Budget defense, ADR-0045) that catches `GraphRecursionError` at the `execute_worker` call site and returns a deterministic "budget exhausted" message with a partial-trajectory summary, instead of letting the exception propagate to the node's generic `except Exception` → Recovery path. The partial trajectory is captured by executing the agent via `stream(stream_mode="values")` (the exception itself carries no state). A single exhaustion counts as one failed attempt — the existing retry loop (Hybrid Retry for Execute, the 3-attempt loop for Test-Writer) stays intact; only repeated exhaustion across all attempts surfaces as failure. The Worker Trace sidecar and Run Observability metrics still execute on the partial trajectory. The three layers: (1) System-Prompt early-exit signal steering the agent to self-terminate before the hard cap, (2) the configurable Recursion Budget crash guard, (3) this graceful call-site catch. Distinct from merely raising the limit (a known anti-pattern that only delays a crash if there is a genuine cycle).
_Avoid_: recursion error fallback, budget catch, soft recursion limit
- **Tool Loop Detection**: The earlier, cheaper layer of the ReAct-loop defense, sitting in front of the Recursion Budget crash guard (ADR-0045). Implemented as a LangChain `AgentMiddleware` (`LoopDetectionMiddleware`) on the Worker's prebuilt `create_agent`: `wrap_tool_call` observes each tool invocation, keying on **name + full canonicalized arguments** into a sliding-window deque, and `before_model` inspects the counts before every model call — at `loop_warn_threshold` (default 3) it injects a steering `SystemMessage` so the model can self-correct, and at `loop_hard_limit` (default 5) it returns `{"jump_to": "end"}` to force-terminate the agent cleanly. This catches a Worker stuck repeating an identical failing tool call (e.g. `pip install` thrash) *before* the budget is spent. Keying on full arguments (not name alone) avoids false-positives on legitimately-varied calls (paginated reads with a different offset); the warn threshold ≥ 2 avoids stopping a transient retry that succeeds on the second attempt; the sliding window (`loop_window_size`, default 10) also catches short oscillations (A→B→A→B…). A force-terminate counts as one failed attempt: `execute_worker` returns a deterministic `[LOOP_DETECTED]` message and the Worker Trace sidecar + Run Observability metrics still run on the partial trajectory (ADR-0016 / ADR-0029), preserving the Graceful Budget Exhaustion contract. Thresholds are co-resolved per-node alongside Model Config; a `loop_hard_limit <= 0` disables it. Distinct from the Recursion Budget (the crash guard, ADR-0045) — loop detection never raises; it routes via `jump_to`.
_Avoid_: agent loop guard, repeat detection, no-progress guard
## Model Routing

- **Per-Node Model Routing**: The resolution of which LLM model each orchestrator node (Plan, Test-Writer, Execute, and later: BinEval, Web Search, PR Judges) uses. Defined per-node in `config/factory.json`, overridable by environment variable, and resolved at runtime via `resolve_model_config(node_name)`. Decouples node-specific model selection from the execute/worker model.
- **Factory Configuration**: The canonical mapping of orchestrator node names to model settings (`model`, `routing`, `temperature`, `options`). Stored as `config/factory.json`. Governs which LLM each node invokes. Not persisted in orchestrator state — re-resolved from the file on each run.
- **Model Config**: The resolved settings for a single node: a dict of `{"model": str, "routing": list|None, "temperature": float, "options": dict|None, "max_tokens": int|None, "fallback_model": str|None, "recursion_limit": int}`. The output of `resolve_model_config(node_name)`. Consumed by `get_chat_model_from_config()` to construct the LLM client. `max_tokens` is set only on structured-output nodes (`plan`, `bin_eval`) to prevent JSON truncation (ADR-0040); other nodes leave it `None` (model/provider default). `recursion_limit` (the per-node Recursion Budget, ADR-0045) is co-resolved per node but consumed by the Worker, not by `get_chat_model_from_config()`.
- **Execute Model**: The model used by the Worker (Execute Node). Persisted as `state["model"]` for backward compatibility with existing `state.json` files from prior runs. Other nodes do not persist their resolved model — they re-resolve from Factory Configuration on each run.
_Avoid_: default model, global model
- **Model Config Override**: An environment variable (e.g., `EXECUTE_MODEL`, `PLAN_MODEL`) that takes precedence over the Factory Configuration default for a specific node. When active, provider routing is disabled (set to `None`), since the override model may not be registered in the factory's routing list.
_Avoid_: env model, model env var

## Loop Metrics

- **Trajectory Length (TL)**: The count of Worker Tool invocations (e.g. `read_file`, `patch_file`, `grep_search`) during a single Execute attempt. A proxy for exploration efficiency: shorter trajectories mean the Worker needed fewer steps to find and make the right changes.
- **Plan Alignment (PA)**: The overlap ratio between files named in the DevelopmentPlan and files actually modified by the Worker, computed as `(Files Planned ∩ Files Modified) / Files Modified`. A proxy for Localization quality: higher alignment means the planner targeted the right files.
- **Token Consumption**: The total tokens consumed during a single issue cycle, broken down by phase — planning (Plan-Node LLM calls, including any Plan Detail Request re-invoke) and execution (ReAct agent LLM calls across Execute-Node and Test-Writer-Node attempts). A proxy for cost efficiency: lets the cost of richer planning context be weighed against the savings from shorter trajectories. Logged as part of the per-cycle Run Observability record.
- **Chunked Evaluation**: The evaluation path for PR Review Judges where a large PR diff is split into per-file chunks, each evaluated independently by the LLM, and the per-chunk verdicts are aggregated into a single per-judge verdict. A judge's overall verdict is `FAIL` if any chunk fails, `NEEDS REVIEW` if any chunk cannot be evaluated, and `PASS` only if all chunks pass. Replaces the previous single-diff-with-truncation path, eliminating the structural unmergeability of large PRs. The external contract (ADR-0019 hidden verdict block, one verdict per judge) is unchanged — only the internal evaluation path differs.
- **Run Observability**: The practice of automatically logging TL, PA, and token consumption on every orchestrator run — not as a one-time benchmark, but as permanent instrumentation accumulated over real runs. Metrics are appended to a dedicated JSONL file (`.agent_logs/metrics.jsonl`), one record per completed issue cycle. `state.json` remains strictly for Stateful Resume — it is not used for metric accumulation. Crashed runs produce no metrics record; only completed runs contribute to trend analysis. Replaces the infeasible golden-dataset approach: architectural decisions are guided by directional trends and published evidence rather than statistically powered ablations.

## Search Integrity

- **Search Integrity**: The discipline of ensuring that claimed web research results are genuine (not hallucinated), verified against live sources, and honestly represented when search tools are unavailable. Governs the meta-layer of AI-assisted ADR research — distinct from the orchestrator's in-codebase `web_search` Worker Tool controls (ADR-0039 annotation capture, ADR-0028 SSRF validation), which ensure the tool itself returns genuine citation data. Established by ADR-0041 after a hallucination incident where a missing search API key caused an agent to fabricate "research-backed" evidence for an ADR.
_Avoid_: search quality, research controls, citation checking
- **Source Quality Tier**: The 4-level hierarchy classifying research sources by authority and accountability: T1 (Authoritative Primary — peer-reviewed publications, official standards, CVE/NVD, official docs, source code), T2 (Authoritative Secondary — vendor engineering blogs, official project docs, reputable industry publications), T3 (Community — Stack Overflow, forums, community blogs), T4 (Unverified — social media, unverified posts, AI summaries without citations). Security-critical and correctness-critical ADR decisions require at least one T1 source; routine decisions may rely on T2 as the highest tier. Informed by Oregon State's "Four Tiers of Sources" and the Elsevier evidence hierarchy.
_Avoid_: source ranking, credibility level, evidence level
- **Search Provenance**: The tracking of source origin, access date, and verification status in ADR references. Each external reference in an ADR's "Inspiration & References" section must include: URL, Source Quality Tier, access date, and a one-sentence verification note. Provides the audit trail for AI-assisted research — a future reader can assess not just *what* was cited, but *how authoritative* the source is and *how it was verified*. ADRs predating ADR-0041 are grandfathered.
_Avoid_: citation tracking, reference metadata, source annotation
- **Fail-Closed Research**: The behavioral contract that when web search is unavailable (missing API key, tool timeout, network failure), the agent explicitly states "web search unavailable — using training data only" and never claims "web research shows" without actual, citation-backed search results. Mirrors the graceful-degradation principle for agent systems: a missing non-essential capability (search) triggers a degraded mode with explicitly reduced confidence, rather than silently substituting parametric knowledge and presenting it as verified. Distinct from the Worker Tool's honest error signal (ADR-0039), which operates at the tool level; this operates at the research-methodology level.
_Avoid_: search fallback, degraded search, silent degradation
- **Framework-First Research**: The discipline of verifying whether an adopted framework (LangGraph, LangChain, OpenRouter, tree-sitter) already provides a native solution before implementing custom code that would duplicate its responsibility domain. Triggers when custom code wraps or substitutes for a framework capability (state persistence, graph execution, checkpoint resume, tool dispatch) — not on trivial utilities outside any framework's scope. When a framework solution is rejected, the ADR must name the native alternative and document a concrete rejection reason (not "unknown"). Established by ADR-0042 after a retrospective found a "Skip First Turn" workaround duplicating LangGraph's native `graph.invoke(None, config)` resume. Sibling to Search Integrity (ADR-0041): that governs whether cited evidence is real; this governs whether the framework was checked at all.
_Avoid_: framework check, capability research, native-first research
- **Security Block**: A permanent, non-retriable failure triggered when the path-safety policy blocks a planned or runtime path (e.g. `.env` in `target_files`). Distinct from transient crashes and verify failures: a security block is quarantined (issue labelled `agent-blocked`), not retried with backoff, and exits with a distinct code (42) so the supervisor can branch it into the circuit-breaker path. Recorded as a `security.block` span event with ERROR status and the `langfuse.trace.tags` tag `security-block` for Langfuse searchability. Established by ADR-0044.
_Avoid_: security failure, path block, safety block
- **Security-Block Quarantine**: The recovery-node behaviour of labelling a security-blocked issue `agent-blocked` (instead of `agent-ready`) so the claim scan skips it on subsequent iterations, preventing a tight loop on a permanently-failing issue. A human can manually remove `agent-blocked` to re-queue the issue after remediation. The existing Unblocking Scan (which scans `agent-blocked` for dependency resolution) remains for human-initiated unblocks.
_Avoid_: issue blocking, security isolation, block-and-skip
- **Security-Block Circuit Breaker**: The supervisor-level protection in `scripts/entrypoint.py` that tracks security-block exits (code 42) over a rolling time window (`collections.deque` of timestamps). If the count reaches the threshold (`AGENT_SECURITY_BLOCK_THRESHOLD`, default 5) within the window (`AGENT_SECURITY_BLOCK_WINDOW`, default 3600s), the supervisor halts with a `CIRCUIT_BREAKER` log and exit code 2. Prevents an active prompt-injection attack from churning across multiple quarantined issues. In-memory only — a supervisor restart resets the window.
_Avoid_: security breaker, block limiter, attack throttle
