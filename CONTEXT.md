# Context: Agentic Developer Core

This document serves as the canonical glossary of domain concepts for the autonomous development loop. It is devoid of implementation details (such as LangGraph nodes or CLI options) and focuses purely on terminology.

## Glossary

- **Autonomous Developer Loop**: The end-to-end lifecycle of an issue being processed by the agent. It spans from claiming a ticket to planning, execution, verification, pull request creation, and merging.
- **Orchestrator**: The high-level coordinator that manages the lifecycle of the loop, guiding work through the distinct phases and handling high-level routing, errors, and task assignment.
- **Worker**: The active agent that performs the actual code-writing, searching, and code modifications within the codebase workspace.
- **Workspace Hygiene**: The practice of cleaning and resetting the workspace (e.g., git cleaning, directory resetting) to guarantee a consistent environment.
- **Stateful Resume**: The capability of the loop to recover from a crash or system restart and resume execution from the exact phase and task it was working on, preserving in-progress work.
- **Verification**: The process of running tests, linters, or other build checks to ensure that modifications meet quality standards and do not introduce regressions.
- **Verification Feedback**: The truncated execution output (maximum 150 lines or 10 KB) captured from a failed verification subprocess. This feedback is persisted in the orchestrator state and fed back to the worker agent in subsequent execution turns to guide self-correction.
- **Block-Based Patching**: The method of modifying code by replacing an exact, unique block of lines (`old_string`) with a replacement block (`new_string`), rather than using line numbers or diff syntax.
- **Planning**: The phase of the autonomous developer loop where the orchestrator uses a language model to analyze a claimed issue alongside a static codebase snapshot to produce a **Localization** — a set of target files and task intents. The plan points the Worker at *where* to work, not *what diff to write*.
- **Localization**: The Plan-Node's output: which files and structural elements (classes, methods, functions) the Worker should touch, plus the intent of each task. Localization never includes line numbers or diff shapes — those are the Worker's responsibility.
- **Edit Synthesis**: The Worker's responsibility during the Execute phase: reading the localized files, reasoning about surrounding code, and writing the actual patches. The plan provides the target; the Worker discovers *how* to make the change through dynamic exploration (read, grep) and ReAct reasoning.
- **Process Supervisor**: A lightweight, zero-dependency Python wrapper (implemented in `scripts/entrypoint.py`) that acts as the entrypoint for the orchestrator container. It validates essential environment variables, verifies network reachability to external services, and manages a resilient execution loop for the orchestrator with exponential crash backoff.
- **Read-Before-Edit Constraint**: A strict safety rule requiring the Worker to programmatically read a file's contents in the current cycle before applying any patches to it, eliminating hallucinated or stale edits. Reading any portion of a file authorizes modifications to the whole file for the duration of the cycle, whereas search queries do not grant modification authority. The record of read files is reset at the start of each phase and upon stateful resume.
- **Blocked by**: A structured markdown section (`## Blocked by`) in an issue body containing references to other issues (e.g., `- #123`). The Orchestrator parses this section, transitioning the issue's label to `agent-blocked` if any referenced issues are open, and restoring it to `agent-ready` once all dependencies are closed.
- **Target Repository**: The remote GitHub repository containing the issues to resolve and the codebase to modify (specified via `GITHUB_REPOSITORY`).
- **Workspace Isolation**: The sandboxing of all worker file edits and command executions inside the local directory specified by `GITHUB_WORKSPACE`, keeping it separate from the orchestrator's own codebase and state logs.
- **Self-Healing Claim**: The two-step programmatic polling process in the Claim-Node that automatically unblocks issues when their dependencies close (transitioning them from `agent-blocked` to `agent-ready`), and claims eligible issues (transitioning them from `agent-ready` to `agent-in-progress`).
- **Pull Request Creation**: The phase of the autonomous developer loop where a pull request is opened to propose the verified codebase modifications for review.
- **Merge Polling**: The process of repeatedly checking the merge status of an open pull request until it is successfully merged or a timeout occurs.
- **Failure Recovery**: The safety process triggered upon total execution failure or timeout, which cleans up local changes and restores the issue's GitHub label back to its ready state, allowing for future attempts.
- **Telemetry**: The mechanism used to collect, record, and export OpenTelemetry-compliant trace spans (such as `orchestrator_loop` and `orchestrator_phase_...`) in-process during the autonomous developer loop execution, supporting crash-resistant JSONL logging and OTLP exporting.
- **Test Writing**: The phase of the autonomous developer loop (implemented in the Test-Writer Node) where the orchestrator uses a language model to write unit/integration tests for the planned changes before implementing them, enforcing Test-Driven Development (TDD) principles.
- **Worker Tool**: A capability exposed to the ReAct Worker agent within the Execute phase (e.g., `read_file`, `patch_file`, `grep_search`, `run_command`). Worker Tools are invoked on-demand by the agent based on what it observes, following the ReAct pattern — not as static pipeline stages. A `web_search` Worker Tool lets the agent research library APIs or error messages inline, only when it encounters a gap it cannot resolve from the codebase alone.
- **Pre-PR Review**: A semantic code-quality grading step within the Verification phase, executed after the deterministic verification command (`make verify`) passes and before a Pull Request is created. Uses a BinEval rubric (binary checks across Completeness, Simplicity, ADR Compliance, Robustness) graded by a lightweight LLM. Failures produce structured feedback fed back to the Worker for in-cycle retry. Acts as a soft gate — it does not block progression permanently.
- **PR Review Judges**: The hard merge-gate evaluation that runs during Merge Polling, post-PR creation. Comprises multiple specialized LLM judges (Syntax/Lint, Test Coverage, Architecture Compliance, Security) each producing a verdict. Any `FAIL` or `NEEDS REVIEW` verdict from the latest-commit reviews unconditionally blocks the merge and triggers Failure Recovery.
- **Language Agnosticism**: Applies exclusively to the Verification path. The Verify Node and its BinEval review operate on language-agnostic inputs (git diff, issue body, generated plan, ADRs). The orchestrator never assumes the Target Repository's programming language for verification — language-specific deterministic checks (lint, type-check, security scans, test coverage) are the Target Repository's own responsibility, enforced via its `make verify` command.
- **Language-Aware Best-Effort Planning**: The Plan-Node, unlike Verification, is permitted to use language-aware signals. It applies structural outline extraction for supported languages (Python, TypeScript) and falls back to the directory tree for unsupported ones. This is a pragmatic tiering, not agnosticism: supported languages get a richer Localization snapshot; unsupported ones still function via the tree alone.
- **Structural Outline**: A compact representation of a source file's declarations — classes, interfaces, type aliases, enums, and method/function signatures *with parameter lists and return types*, extracted without file bodies, docstrings, or comments. Appended to the codebase snapshot in the Plan-Node prompt as a Localization aid. Parameter lists disambiguate methods with similar names across files. Outlines are *hints*, not ground truth: a misparsed signature is a planning signal, not a contract. The Worker's Read-Before-Edit Constraint remains the safety net against hallucinated edits.
- **Outline Fidelity**: Outlines for all supported languages (Python, TypeScript) are produced by tree-sitter via `tree-sitter-language-pack` — a single dependency providing pre-built grammar wheels with one unified query API. Both languages get robust, accurate outlines from the same tool. Unsupported languages (Go, Rust, etc.) fall back to the directory tree alone. Adding a new language's outlines requires only its tree-sitter grammar, not a new hand-rolled parser.
- **Plan Detail Request**: An optional field in the DevelopmentPlan output allowing the planner to request full Structural Outlines for specific files whose outlines were truncated by the cap. If non-empty, the Plan-Node fetches those outlines, enriches the prompt, and re-invokes the LLM once. Bounded to a single follow-up call — the Plan-Node is not a ReAct agent and does not explore freely; it makes one targeted request for more detail, then produces the best plan it can. The Worker compensates for any remaining gaps during Execute.
- **Web Search**: A Worker Tool that invokes OpenRouter's server-side `web_search` tool, letting the Worker research library APIs, error messages, or unfamiliar patterns inline during the Execute phase. Search runs server-side at OpenRouter, so SSRF risk is near-zero.
- **URL Fetch**: A Worker Tool that retrieves the text content of a specific URL (e.g., a documentation page found via Web Search). Enforces SSRF protection (blocks private, loopback, link-local, reserved, multicast, and unspecified IP ranges) and optional domain allowlisting via `config/sources.yaml`. Response is truncated to a maximum length to bound token consumption.
- **Trace Export**: The mechanism by which recorded telemetry spans are sent to an external collector for visualization and analysis. When `LANGFUSE_PUBLIC_KEY` and `LANGFUSE_SECRET_KEY` environment variables are set, spans are exported to Langfuse Cloud with Basic auth, and session-level baggage (`langfuse.session.id`) is attached to group all traces for a single issue cycle. When Langfuse keys are absent, spans fall back to the generic OTLP endpoint (`OTEL_EXPORTER_OTLP_ENDPOINT` or `host.docker.internal:4318`). This preserves the graceful degradation mandated by ADR-0016: tracing never breaks execution if the exporter or library is unavailable.
- **Worker Trace**: A serialized record of the Worker's full ReAct conversation (AI reasoning, tool calls, tool results) persisted to a JSONL file under `.agent_logs/` after each Execute attempt. Used exclusively for post-hoc debugging and observability — it is never loaded back into the loop or injected into retry attempts. The retry feedback mechanism remains the truncated Verification Feedback (Reflexion pattern), not raw trajectory replay.
## Model Routing

- **Per-Node Model Routing**: The resolution of which LLM model each orchestrator node (Plan, Test-Writer, Execute, and later: BinEval, Web Search, PR Judges) uses. Defined per-node in `config/factory.json`, overridable by environment variable, and resolved at runtime via `resolve_model_config(node_name)`. Decouples node-specific model selection from the execute/worker model.
- **Factory Configuration**: The canonical mapping of orchestrator node names to model settings (`model`, `routing`, `temperature`, `options`). Stored as `config/factory.json`. Governs which LLM each node invokes. Not persisted in orchestrator state — re-resolved from the file on each run.
- **Model Config**: The resolved settings for a single node: a dict of `{"model": str, "routing": list|None, "temperature": float, "options": dict|None}`. The output of `resolve_model_config(node_name)`. Consumed by `get_chat_model_from_config()` to construct the LLM client.
- **Execute Model**: The model used by the Worker (Execute Node). Persisted as `state["model"]` for backward compatibility with existing `state.json` files from prior runs. Other nodes do not persist their resolved model — they re-resolve from Factory Configuration on each run.
_Avoid_: default model, global model
- **Model Config Override**: An environment variable (e.g., `EXECUTE_MODEL`, `PLAN_MODEL`) that takes precedence over the Factory Configuration default for a specific node. When active, provider routing is disabled (set to `None`), since the override model may not be registered in the factory's routing list.
_Avoid_: env model, model env var

## Loop Metrics

- **Trajectory Length (TL)**: The count of Worker Tool invocations (e.g. `read_file`, `patch_file`, `grep_search`) during a single Execute attempt. A proxy for exploration efficiency: shorter trajectories mean the Worker needed fewer steps to find and make the right changes.
- **Plan Alignment (PA)**: The overlap ratio between files named in the DevelopmentPlan and files actually modified by the Worker, computed as `(Files Planned ∩ Files Modified) / Files Modified`. A proxy for Localization quality: higher alignment means the planner targeted the right files.
- **Run Observability**: The practice of automatically logging TL, PA, and token consumption on every orchestrator run — not as a one-time benchmark, but as permanent instrumentation accumulated over real runs. Metrics are appended to a dedicated JSONL file (`.agent_logs/metrics.jsonl`), one record per completed issue cycle. `state.json` remains strictly for Stateful Resume — it is not used for metric accumulation. Crashed runs produce no metrics record; only completed runs contribute to trend analysis. Replaces the infeasible golden-dataset approach: architectural decisions are guided by directional trends and published evidence rather than statistically powered ablations.
